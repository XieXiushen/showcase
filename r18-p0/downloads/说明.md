# 本地视觉服务自检包（三段判据）

配套文章：《12GB 显卡跑视觉模型：首 token 13.4 秒 → 0.5 秒，差别只在 mmproj 放哪》
（期 1 定稿 `org\articles\wechat-low-compute-local-llm.md`）

本包解决一个问题：**模型「跑起来了」和「真的在 GPU 上跑」是两件事**，而第二件事
可以在自己机器上 30 秒判掉，不需要相信任何人的数字。

---

## 包内文件

| 文件 | 作用 | 怎么用 |
|---|---|---|
| `自检.cmd` | 一键跑三段判据（启动目录 / 显存与进程 / 驻留显存区间） | 双击，或 `自检.cmd "D:\ollama\bin\llama-server.exe"` |
| `verify_vision.py` | 真调一次视觉模型，量首 token、端到端、显存峰值，并核对已知真值 | `python verify_vision.py [图片路径]` |
| `自检-实跑输出.txt` | 本机真实终端输出一次（未编辑），作为对照样张 | 直接看 |
| `说明.md` | 本文件：每段判据的预期输出样例与判读一句话 | 直接看 |

运行前提：Windows + NVIDIA 独显（`nvidia-smi` 在 PATH 里）+ llama.cpp 的
`llama-server.exe`；`verify_vision.py` 还需要服务已监听 `127.0.0.1:8081`。

## 判据一：启动目录与 CUDA DLL 位置

看什么：`llama-server.exe` **同级目录**里有没有 `ggml-cuda.dll` / `cublas64_13.dll`。

预期输出样例（本机 OK 的那一组，`D:\ollama\bin`）：

```
  启动目录  : D:\ollama\bin\
  同级 DLL  :
concrt140.dll
cublas64_13.dll
...
ggml-cuda.dll
...
  cuda_v13 子目录 DLL :
    (无 cuda_v13 子目录)

  判定: [OK] CUDA 运行库与 exe 同级，-ngl 99 有机会生效。
```

风险形态（DLL 只在 `cuda_v13\` 子目录里，exe 同级没有）：

```
  判定: [风险] exe 同级没有 ggml-cuda.dll / cublas64_13.dll。
```

**判读一句话**：同级有 `ggml-cuda.dll` 才能谈 `-ngl`；只在子目录里时，llama.cpp
不会进子目录找，模型会整段落到 CPU 上，而且**进程不报错**——这就是「无报错的崩塌」。

---

## 判据二：显存占用与占显存进程清单

看什么：整卡 `memory.used / memory.total`，以及进程清单里有没有 `llama-server.exe`。

预期输出样例（本机实测，服务运行中；下面是 `自检-实跑输出.txt` 里的原样行）：

```
name, driver_version, memory.used [MiB], memory.total [MiB]
NVIDIA GeForce RTX 5070, 581.29, 8548 MiB, 12227 MiB
```

```
|  0%   41C    P8              9W /  250W |    8548MiB /  12227MiB |      0%      Default |
```

进程清单里应有这一行（有它就是真的开着服务）：

```
|    0   N/A  N/A           32208      C   D:\ollama\bin\llama-server.exe        N/A      |
```

**判读一句话**：整卡数字里含桌面常驻（本机桌面约 1331 MiB），所以「服务在跑」时
应当是 6 GB 以上；只有 1300 MiB 上下说明权重根本没上卡。

## 判据三：模型加载后驻留显存是否落在预期区间

看什么：连续采样约 12 秒取到的显存峰值。区间与出处：

| 情形 | 加载后 / 峰值（MiB） | 出处 |
|---|---|---|
| 7B-VL + mmproj 上卡（推荐配置） | 8268 / 8369 | `D:\ollama\bench-r14\result-G4.json` |
| 7B-VL + mmproj 留 CPU | 6284 / 6287 | `D:\ollama\bench-r14\summary.txt`（G1 组） |
| CPU 退化（`-ngl 99` 被忽略） | 1332 / 1342 | `D:\ollama\bench-r14\g6.out` |
| 本次实跑（桌面还开着浏览器等） | 8551 / 8556 | `自检-实跑输出.txt`（判据三那两行） |

预期输出样例（`自检-实跑输出.txt` 原样行）：

```
  最后一次采样: 8551 MiB
  采样峰值    : 8556 MiB
  判定: [OK] 权重已上卡(本机 G4 组记录: 加载 8268 / 峰值 8369 MiB, 见 result-G4.json)
```

注意：本机本次读数是 8556 MiB，比 G4 记录的峰值 8369 MiB 高，原因是判定当下桌面
还开着浏览器等程序，显存读数含这些占用。**判据三看的是量级，不是小数点**：
6000 MiB 以上即已上卡，1300 MiB 那一档才是退化。

判据阈值（脚本内写死）：

| 峰值 | 判定 | 含义 |
|---|---|---|
| < 2000 MiB | `[FAIL] 可能已退化 CPU` | 权重没上卡，回判据一查 DLL 位置 |
| 2000–5999 MiB | `[WARN]` | 只卸载了部分层，或别的程序在抢显存 |
| 6000–9500 MiB | `[OK]` | 与 G4 同档 |
| > 9500 MiB | `[WARN]` | 先关掉其他占显存的程序再测 |

**判读一句话**：判据三给出的是「结果」，判据一给的是「原因」；三段里任何一段
FAIL/WARN，都先修再交付，不要靠「感觉慢」下结论。

## 真实自检命令与读数如何对照文章

文章里那一行配置：

```
llama-server -m qwen2.5-vl-7b-q4km.gguf --mmproj mmproj-F16.gguf -c 8192 -ngl 99 -fa on -t 12
```

自检后应当能对上的读数（同机同图同 prompt，全部来自 `D:\ollama\bench-r14\`）：

| 项 | 文章（G4 组） | 本次实跑 | 说明 |
|---|---|---|---|
| 整卡显存 加载/峰值 | 8268 / 8369 MiB | 8550 / 8556 MiB | 差异来自桌面与其他程序占用，同档 |
| prompt tok/s（1069 token） | 2322.94 | 未测（本脚本不打服务端计时） | 想看这一项去服务端日志 `prompt eval time` 行 |
| decode tok/s | 116.71 | 未测（同上） | 同上 |
| 首 token | 冷启动 0.586 s / 缓存命中 0.031 s | 0.123 s | 实跑时 prompt 完全相同、命中缓存，所以明显快于冷启动 |
| 关键真值 | 6.71% / P2 / 7 日内回补 | 4/4 命中 | 逐字命中 |

**别把这两张表混着报**：首 token 必须分清「冷启动」还是「缓存命中」，文章 §3.1
的免责声明也是这个口径。

## 已知限制（照实写，不粉饰）

1. 三段判据只覆盖三类已复现的故障：DLL 位置、显存未上卡、显存异常。它**不覆盖**
   端口占用、驱动版本不匹配、量化文件损坏——那几类看服务端日志的报错行。
2. `verify_vision.py` 只报首 token 与端到端，**不打服务端 prompt/decode tok/s**；
   那两项要读 `llama-server` 自己的 `prompt eval time` / `eval time` 行。
3. 首 token 受缓存影响极大（本机缓存命中 0.031 s、热·全量 0.481 s、冷启动 0.586 s），
   拿实跑数字和别人的数字比之前，先确认口径一致。
4. `自检.cmd` 里判据三的阈值是本机实测区间，换卡要按自己机器的读数重设。
5. 批处理踩坑两条（都实测过）：文件必须 CRLF 行尾；`for /f` 里调用 `nvidia-smi`
   带逗号参数会被吃掉，所以脚本改写临时文件再读回。
